## Notes

If we have Supply and Deliver order concurrent (different items under the same order - two parallel orders is not supported) then there should be an order items dependency management to ensure that the services are modified in the right sequence
In upgrades -> Supply then Delivery (if the new deliver is higher than the old Supply)
In downgrade -> Delivery then Supply
If a modify Delivery is received to change the Delivery to a higher speed than the Supply, then the order should be rejected
Supply 100Mbs, Delivery 60Mb - apply this logic to the downstream speed
Modify increase the Delivery to 80Mb -> accepted
Modify increase the Delivery to 120Mb -> rejected
Modify (in a single service order) Supply to 120, Delivery 160 -> rejected
Modify (in a single service order) Supply to 120, Delivery 120 -> change the Supply first then the Delivery
Modify (in a single service order) Supply to 40, Delivery 40 -> change the Delivery first then the Supply
This logic is applicable to only Supply-Delivery which has a 1:1 relationship, G4 for now.
The solution to allow extension in the future to support these scenarios. 
In this project scope, the validation will be between MillhouseG4Supply and SubscriberTrimming delivery, or between MillhouseG4Supply and CarrierRibbon delivery services.
